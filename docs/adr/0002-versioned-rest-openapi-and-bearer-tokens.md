# Versioned REST + OpenAPI via the community generator, with opaque Bearer tokens

External consumers (scripts, mobile clients, AI agents, plain `curl`) could only reach the API through the typed in-app transport, which needs batching plus superjson — unusable from generic HTTP tools — and delegation meant sharing a session cookie, since no revocable Bearer credential existed. We decided to ship a versioned plain-JSON REST mount alongside the unchanged typed transport, described by an OpenAPI Document generated from the routers with a live Reference UI, authenticating via either the session cookie or a new opaque personal access token. Both resolve to the same user-with-roles, so the existing coarse and row-level permission checks apply unchanged. The whole surface moved to Zod 4 first, atomically, so every annotation and output schema targets the final syntax.

## Considered Options

- **Official docs-only alpha generator instead of the community REST-capable fork**: the official package describes the tRPC protocol but produces no callable plain-JSON Operations, and it rides a per-release alpha line. Rejected — the chosen generator works on the current Zod line and the current tRPC v11 minor (dependency add only, no transport upgrade), emits callable Operations, and carries no per-release alpha risk. The official package stays a future option: the versioned mount lets v1 stay frozen while a v2 is evaluated.
- **Annotate on Zod 3, migrate later**: writing REST annotations first and migrating validation afterwards. Rejected — every annotation and output schema would be reviewed twice, and the bigger-blast-radius migration (post/auth/role schemas, inline procedure inputs, form resolvers, server error formatter) is the schedule risk, so it landed atomically first even though it touches auth forms and role validation far from "docs".
- **Reusing JWT/session lifetime for external access instead of opaque tokens**: signing external credentials as JWTs. Rejected — opaque tokens decouple external-caller lifetime from session lifetime and give per-token revocation and expiry, at the cost of one small token table plus a migration. Tokens are full-impersonation by design: a valid token grants exactly the holder's roles, never elevation.
- **Putting admin management on REST now**: documenting and mounting the privileged surface alongside posts. Rejected — its auth story is unsettled, so the admin surface stays typed-transport-only: unannotated, auto-excluded from the Document, and 404 on the REST mount by construction.
- **Granular token scopes now** (read-only keys, per-resource scopes): deferred — v1 tokens carry expiry and revocation only.

## Consequences

- Transport split: the typed mount is byte-identical (batched, superjson, cookie-only); the new versioned REST mount serves the same routers as plain JSON with ISO datetimes and no superjson envelope. The `/api/v1` prefix reserves room for breaking REST changes without touching the typed transport.
- Scope: 8 Operations over 5 paths in 2 tags (posts, dashboard) — post collection, fetch/create/patch/delete by id, latest, greeting, dashboard stats. Only the two public reads are unauthenticated; every protected Operation declares both auth schemes (either satisfies). Strict shared output schemas are enforced at the controller tier, with dates serialized to ISO there so the contract already holds on the typed transport itself.
- Dual auth on REST is Bearer-first with cookie fallback only when no Bearer is presented: a presented-but-invalid/expired/revoked Bearer fails closed (401 on protected Operations) and never inherits the browser session, so a leaked token cannot silently ride a cookie. The typed transport stays cookie-only. Token lifecycle (create/list/revoke) is typed-transport-only and excluded from the Document, avoiding a bootstrap paradox where the credential-issuing surface would need the credential to be described.
- Error mapping: unauthenticated to 401, grant/ownership denial to 403, missing record to 404; visibility scoping is preserved per transport (USER-scoped vs privileged-wide lists return the same sets on REST as in-app).
- Document pipeline: generated once at module load (build time for the static route, never per request), served from a static JSON route, rendered by a live Scalar Reference page that needs no token setup thanks to the cookie fallback. The generator's flat-input constraint is accepted; non-flat inputs are reshaped at the controller boundary.
- Vocabulary follows the glossary: Procedure vs Operation, Document vs Reference UI vs REST mount, Bearer token vs session. Existing role-invariant decisions (every user holds at least one role; union-of-grants; defense-in-depth denial) are respected and unchanged.
- Explicitly out of scope: migrating the typed transport, adopting the official generator, admin on REST, granular scopes, session-system changes, rate limiting beyond the existing middleware, a v2 surface, and client SDK generation beyond the Document itself.
